## Summary
Byte-for-byte replay of upstream apache/jackrabbit-oak PR #2409 (commit `f14f6e3e`, 2026-02-16) on top of its parent commit `54b40abd` (branch `replay-base`), opened in this fork so the change can be reviewed again as it was originally submitted.

The change upgrades `oak-blob-cloud-azure` from the legacy Azure Storage SDK v8 to SDK v12 while keeping both backends:

- new `v12/AzureBlobStoreBackendV12` + `AzureBlobContainerProviderV12`, selectable via `blob.azure.v12.enabled` (default: v8 via `AzureDataStore.createBackend()`)
- legacy code moved to `v8/AzureBlobStoreBackendV8`, `v8/AzureBlobContainerProviderV8`, `v8/UtilsV8`
- direct-binary-access upload limits consolidated into shared `AzureConstants`:
  ```java
  AZURE_BLOB_MIN_MULTIPART_UPLOAD_PART_SIZE = 256L * 1024L;          // 256 KB
  AZURE_BLOB_MAX_MULTIPART_UPLOAD_PART_SIZE = 4000L * 1024L * 1024L; // 4000 MB
  ```
  which both `AzureBlobStoreBackendV8.initiateHttpUpload()` and `AzureBlobStoreBackendV12.initiateHttpUpload()` now read
- Azurite-based tests (`AzuriteDockerRule`, image `mcr.microsoft.com/azure-storage/azurite:3.29.0`) cover both backends

45 files changed, +14,895 / -1,555.

	🔴 **Large binary uploads use oversized blocks**

	When a file exceeds 4000 MiB, `uploadBlob` sets its block size to the entire file length. Azure limits each staged block to 4000 MiB, so the binary upload fails.

	<details>
	<summary>Learn more</summary>

	The file upload switches to staged blocks once its size exceeds `AZURE_BLOB_MAX_SINGLE_PUT_UPLOAD_SIZE`. With a block size equal to `len`, that stage is one block regardless of file size. [AzureConstants](https://github.com/michael-cog-gtm/jackrabbit-oak/blob/f14f6e3ee6bb838308b8c997d794756932ec4ae7/oak-blob-cloud-azure/src/main/java/org/apache/jackrabbit/oak/blob/cloud/azure/blobstorage/AzureConstants.java#L183-L200 "oak-blob-cloud-azure/src/main/java/org/apache/jackrabbit/oak/blob/cloud/azure/blobstorage/AzureConstants.java:183-200") sets the supported per-block limit to 4000 MiB and permits total binary sizes far larger.

	**Example:** Writing a 5 GiB binary stages a 5 GiB block rather than several smaller blocks, and Azure rejects the upload.

	**Recommended fix:** Set the parallel transfer block size to a bounded size below the service's limit, and retain the configured concurrency for large uploads. Test a multi-block file with V12.

	</details>

	When `azureConnectionString` is set, `getBlobContainer` bypasses the proxy configured in `properties`. The connection-string builder also omits `retryOptions`, so configured network and retry settings do not apply.

	<details>
